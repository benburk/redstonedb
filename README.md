# redstone-database

A collection of Minecraft redstone schematics, named so they can be sorted, searched, and parsed.

- [naming.md](naming.md): the filename scheme.
- [glossary.md](glossary.md): category names, modifiers, and their abbreviations.
- [conventions.md](conventions.md): how builds are laid out in-world, and the block palette.
- [metadata.md](metadata.md): candidate fields not yet in the database.
- [features.md](features.md): planned lint checks and export options.

Each part of the scheme is marked either decided or open.

## rsdb

`rsdb` is a command-line wrapper around a SQLite database, `redstone.db`. The database is the source of truth: it holds each `.schem` file, its fields, and its tags. Filenames are generated from it on export; see [naming.md](naming.md). `migrations/` defines the tables, squashed into one schema on 2026-10-08; the server and the CLI apply pending migrations when they open the database.

`redstone.db` is not in git, so back it up on its own. A fresh checkout starts with no database; the CLI or the server creates an empty one on first use. `rsdb` writes every change into the file before it exits, so copying `redstone.db` alone is a complete backup.

```sh
just rsdb add adder.schem --category adder --orientation vert --encoding bin \
    --width 8 --latency 3 --builder cullback --built-on 2026-10-07 --tag alpha
just rsdb list --tag alpha
just rsdb search register vertical alpha -torchless
just rsdb show 23a9
just rsdb set 23a9 --latency 4
just rsdb tag 23a9 torchless carry_lookahead
just rsdb export 23a9 --out ~/.minecraft/config/worldedit/schematics
just rsdb remove 23a9
just rsdb add slice.schem --category adder --orientation horz --encoding bin \
    --width 1 --stack west=2,max=7 --stack north=4,max=3
just rsdb export 23a9 --copies west=7,north=3 --out .
just rsdb tags
just rsdb define-tag carry_lookahead --kind other
just rsdb define-tag pistonless --kind restriction
```

- `add` takes any glass corner markers out of the file and fits its box tightly, as uploads do, and writes each sign's lines as plain text, however the file held them, such as in a text component's `extra` parts, with commas taken out; see [conventions.md](conventions.md). It reads the size from that box, leaving out any outer layer of nothing but the interface, input blocks with their levers, and outputs, output blocks with the dust, repeater, or comparator standing on them, since an input sticking out is driven there and an output sticking out is read there; and it rejects a file already stored. Stacking goes by the box less only the inputs, as a copy's step may reach past its outputs. `rsdb reread` reshapes and measures every stored build again after the rules change. It accepts Sponge `.schem` files, versions 2 and 3.
- `add` lints the file against [conventions.md](conventions.md) first and refuses it if it breaks one, unless given `--force`. `just rsdb lint <file or id>` runs the same checks on their own.
- Each adder, incrementer, decrementer, inc/dec, stateless multiplier, stateless converter between binary and BCD, ALU, register, absolute value, and carry out of up to 32 bits is simulated in [MCHPRS](https://github.com/MCHPR/MCHPRS)'s redstone compiler, Redpiler, through every combination of its inputs when they come to at most 20 bits, as for an 8-bit adder or multiplier. A wider adder takes every case of each byte, with a carry into it from the bits below and without, and every pairing of test patterns: none and all bits set, alternating runs of one, two, and four bits at every shift, and each bit alone set or clear, with carry in each way. The patterns make the longest carries, such as all ones plus one, which random sums almost never do. A wider multiplier takes every value of each byte of A with every value of each byte of B, every value of each byte of C, for A × B + C, with A and B clear or all set, and every pairing of the patterns. Its product is checked against as many low bits as its outputs hold together, yellow lowest, so one that gives only the low half passes too; one with a control line, such as a clock, is sequential and skipped. Either way, the simulator first lets the saved file settle as the game would, in case it was saved mid-change or edited by hand, then flips the levers as a player would, waits until nothing changes, and reads each output bit from the dust, repeater, or comparator standing on its block, which carries it out of the build, as on while that is on, however the block below is powered; a bare output block is on while it is powered. An adder whose A, B, and output differ in bit count, or that has inputs or outputs an adder does not, is broken, which counts as failing; the output may hold the carry as its top bit when there is no carry out line. Barrels, furnaces, and hoppers give a comparator their signal strength, though a hopper moves no items, so a hopper clock would simulate wrongly. A build using a block Redpiler does not model, such as a piston or observer, is skipped and the block named, as is a signal-strength input or a stained-glass output. When every sum is wrong but flipping carry in puts them all right, the result says its lever is saved the wrong way round.
- An incrementer is checked against A plus 1, or with a control line, A plus the line; a decrementer against A minus either; neither need sign its lone control or status line, which they take as their increment or decrement and carry or borrow out, as an adder takes its carry lines; and an inc/dec against plus 1 one way of its line and minus 1 the other. Whichever its category allows that it gets most right names its cases, as `A + increment`.
- An absolute value takes one input, A, read as a signed number in two's complement, and is checked against its magnitude, unsigned in as many bits as A, on as many low bits as its outputs hold: A when its top bit is clear, else −A, so the most negative A gives itself, as negating it does, whether a build means that as itself or as its unsigned magnitude. Every value of A is tried up to 20 bits, beyond that each byte's values and the test patterns.
- A carry out takes two operands, A and B, of one width, and an optional carry in, and gives only the carry of A + B (+ carry in) on one line, a status line or a 1-bit output, as a fast carry or an A ≥ −B test does; its lone control and status lines need no signs, as an adder's do. It is checked on every case up to 20 bits of inputs, beyond that on the adder's cases, and timed by its one line, since a build whose only outputs are status lines goes by them.
- A binary-to-BCD converter takes one input, A, and is checked against A in binary-coded decimal, each decimal digit in four bits, the ones digit lowest, across its outputs together; outputs too few for A's largest value make it broken. A BCD-to-binary converter is driven only with values of A whose every digit is decimal and whose number its outputs can hold, as a 10-bit BCD input into eight output bits takes 0 to 255, and checked against that number. Its timing takes the same values, so values it was never built for cannot make it look unsynced. When some cases are wrong but every one is right with one of A's levers that is saved on driven as a plain input, the result says that lever is saved on by mistake, since a lever saved on marks an inverted input. Every value is tried up to 2^20 of them; beyond, a binary input takes every value of each byte, the test patterns, and each power of ten and the number before it, and a BCD input every number below 1,000, each digit's every value alone, each run of nines, and its largest. One with a control line is sequential and skipped.
- An ALU takes two operands, A and B, of one width, and control lines whose signs name the operations each takes part in; see [conventions.md](conventions.md). Each operation a sign names is checked on every value of A and B, choosing it by flipping every line that names it from where it was saved: add as A + B, plus the carry in when a line is named so, sub as A − B, the bitwise and, or, xor, nand, nor, and xnor, and shl, shr, and asr as A shifted a place, asr keeping the sign bit. With at most six lines, each other combination of them is tried on the test patterns, and one that gets an operation no sign names right in three cases in four, as an ALU that adds with every line off, is checked on every case too and listed with its lines, as `add (no lines on)`. A status line is checked where its meaning is plain: a carry out, named `carry` and `out`, for add and sub, as the adder gives it, so a sub, A + ~B + 1, carries when it borrows nothing; an overflow, as signed, for add and sub; an `lsb shift out`, the bit a shift right drops, for shr and asr; and a zero for every operation. A wrong case names its operation. Each operation is timed with its lines held, and the ALU's latency is the slowest's, synced when every operation's result is. An ALU's signs tick its flags for the operations they name beyond adding and subtracting, NAND, NOR, XNOR, and ASR among them. A build's page lists every flag of its category, yes or no, so an ALU without a shift left says SHL no.
- A register's cells are found from its magenta lines, a button or a line signed `write` writing and a lever or a line signed `read` reading, in `src/simulate/register.rs`: with every cell holding 0 and then each alone holding all ones, the buses are read with every read as saved and with each flipped alone, and a read whose flipping changes how the cell shows is its own, on the bus where it does. A read that shows its cell as saved and stops when flipped is inverted, and is held flipped while not reading; one whose cell's all ones show as all zeros puts it on the bus inverted, and its cases expect the complement. What the buses show with no read on is taken from the build, 0 or all ones for an inverted bus, and must not change with what the cells hold. Every value up to 8 bits, beyond that the test patterns and each byte's values, is written into every cell, each cell offset so that they differ; then the data bus changes, every read off must leave the buses empty, and each read alone must show its cell on its bus and nothing elsewhere. A wrong case names its cell, or `every read off`, and a register whose buses show its cells with every read off is told its reads do not keep them off the bus. Its latency is data in to data out, so that a data loop's is its ALU's plus its registers': with a cell's write held open and its read on, from its data in changing until the bus shows it, the control lines no part of it. A cell whose bus is empty while its write is open, and which shows its data once the write closes, its lever turning off or its button springing back, takes its data as its write closes: its latency counts from its data in changing on the tick the write closes, and its write from the write closing. A register that takes its data only as its write opens is timed from the write's button instead. Its timing also gives the ticks from a write's button until the bus shows the value, and each read, from a read lever turning on to the bus settling. Copies stack west into a register file or a wider register: the shortest step west, up to the build's width, at which two copies' cells all store and read right, either as more cells through data buses driven and read at the first copy's end, or as more bits through control lines driven at the first copy's end, then the most copies that do, up to 16, as a line that runs too far fails; a register whose stacking is found takes it in place of its builder's west step, with that many copies at most, keeping their other directions, and a wider register's orientation becomes horizontal; any other keeps what its builder gave. The 8-bit fixture's two cells read in 6 ticks and write in 8, and four copies 4 west make 8 registers.
- A stackable build's page has a Stacking in game section, from `stack::review`, for each way it stacks: the `//rstack` command, with a count of its most copies or 8, and when it has parts only its first copy keeps (gray blocks, inputs the copy before feeds, and data blocks whose buses run on through the copy before), downloads of the build without them and of the parts alone, `/schematics/<id>/download?part=without|first&direction=<way>`, to paste, stack, and paste back with `//paste -a`. Where the simulation did not find the stacking, the section warns of each spot where two copies hold different blocks, containers by their strength, naming where the later copy's block is in the file and, for a torch, dust, repeater, or comparator, the block it rests on, which made gray would leave both out of later copies, and of two copies that do not make a bigger build of its shape. A later copy's block always stands, so a wrong step no longer refuses a save; the warnings say what it does.
- The upload page guesses what a file is before anyone says: it runs a few hundred telling sums, such as all ones plus one or alternate bits, through each test its inputs and outputs fit, which takes milliseconds even for a hex build, and starts the category, for an incrementer whichever of incrementer, decrementer, or inc/dec it does, as the one that comes out right most often, if three cases in four do. It says what it saw, such as "Looks like an adder: A + B + carry in, right in 2,048 of 2,048 quick cases", and the category stays the uploader's to change.
- An adder that gets every sum right is then stacked as its bits suggest: copies a bus's length apart along the way its bits run, carrying on its spacing, or for a 1-bit adder the shortest step up, west, or north whose copies add right, its carry in to its carry out winning a tie, enough of them that one sits between two others and the stack reaches a copy past the 15 blocks dust carries a signal, so a path through copies with no repeater or torch to renew it fails: 9 copies of a 1-bit slice 2 wide, 3 of an 8-bit adder 16 high, and no more than the 32 bits the simulator tests. The cheapest checks come first and the first to fail ends it, in milliseconds: a carry in to take the carry from the copy before, bits spaced in a repeating pattern, copies that fit together and read as one adder, a stack that settles, and sums whose carry crosses between copies. Only a stack that passes those takes the full test. One that adds right then is taken to stack any number of times, and an adder's stacking is set from it, that step with no limit on copies, or none, so the details form asks only about other categories' stacking; the result shows under the build's cases. Its orientation is set from the step too, as copies that add up run the way the bits do: vertical for a step up, horizontal for one west, and diagonal for one west and up, which a 1-bit adder's lone input cannot show.
- Each build's file is read for the oldest Minecraft: Java Edition release it works in: the release that added the newest redstone component or mechanic it uses, in `src/works_from.rs`, building blocks left out. Repeater locking, a dot of dust beside a block it would once have powered, and a block of redstone beside a comparator are found from how components sit, not just which blocks are there. It is read whenever a file is stored, once for builds from before it was kept, and again by `rsdb reread`. A build's page shows it with the component that sets it, as `1.16 (target block)`; a build that works from Alpha carries the `alpha` restriction, read from the file like `torchless`; and search finds the builds that work in a release with `version:1.12`.
- A stackable build's page shows, beside its size, its size per copy: its size with its step in place of its length along each way it stacks, which a stack grows by with each copy, as copies may overlap. Its volume is per copy too, wherever it shows and sorts and on the leaderboards, since that is what a wider stack costs: a 1-bit adder 4×4×6 that stacks every 2 up is 48 blocks per copy, though its box is 96. A diagonal step grows no box, so a build stacking that way goes by its box.
- An adder that gets every sum right is then timed, in ticks from when A, the lime input, changes. Each other input's tick is the latest it may change without delaying an output, negative when it must come before A; each output's latency is the last tick it settles by, taken where it reaches the repeaters or comparators standing on its blocks when every block has one carrying it out of the build, so their delay is left out and noted; and the build is synced when every output changes only once, all its bits on the same tick. The changes measured are each input alone, from 0 to every value and back with the others at every combination, and every input together, each at its tick, from all off to every combination and back. An adder too wide to try every value takes the test patterns instead, for each input alone and all together. A worse change may exist among those not tried. Timing an 8-bit adder takes about 17 seconds of one core, spread over every core; a 16-bit one, with the patterns, under a second.
- The width of an adder, incrementer, decrementer, inc/dec, ALU, register, absolute value, or carry out is its lime input's bit count, read from the file rather than typed, as are its orientation, the way those bits run, and its encoding; only an adder's flags, its carry lines, are read too, and a timed build's latency is that of its slowest data output, leaving out status lines such as carry out, and its synchronized is whether it is synced. Each is written into the build when the file, category, or width changes: `add`, `set`, and `reread` do so at once, and uploading, editing, or publishing a new version runs them in the background; see below. The details form shows the width it read and that latency and synchronized are measured, in place of their fields. `just rsdb simulate <id>` runs the cases and timing again regardless, and with no id, of every build with a test, as is needed once the simulator changes.
- `--standardize` brings a downloaded build into the palette before importing it. Slabs, stairs, and glass become white stained glass, and every other solid block becomes white concrete, keeping redstone components, inputs, and outputs. Gray blocks become white too, unless `--keep-gray` keeps them as the logic only a stack's first copy needs; the upload and new-version pages have the same choice, Whiten gray blocks too, ticked by default. Old corner markers, and any other plain glass touching nothing but air, are removed, as are signs on a block that is neither an input nor an output, such as a note of the build's date, which label nothing; a sign of any other wood becomes oak. The box is fitted tightly. Inputs (levers on lime, light blue, or magenta blocks) and outputs (yellow concrete or yellow stained glass) must already be marked, since they are what survives.
- `--conventional false` marks a build, such as a display, that follows its own layout. `add` skips the lint for it, and its page does not read inputs and outputs from it. It is measured by its whole box.
- `--stack` marks a build as a stackable slice, once for each direction it stacks along: how far each copy sits `west`, `up`, or `north` of the one before, and optionally the `max` copies that work. Giving `--stack` to `set` replaces the stored directions; `--unset stacking` makes a build unstackable. `export --copies` writes the copies joined into one schematic, as [conventions.md](conventions.md) describes: a plain count for a build that stacks one way, or a count per direction such as `west=7,north=3`. `export --markers` puts a glass block off each corner, for WorldEdit to select the build by.
- `--synchronized true` or `false` records whether every output bit settles on the same tick; left out, it is unknown.
- `set --unset latency` makes a field unknown again; `--unset` takes `width`, `latency`, `synchronized`, `builders`, `contributors`, or `built-on` and repeats.
- Ids can be shortened to any unique prefix.
- A build's category is a standard one, such as `adder`, or any other name; every build also has a design, `other` unless its category lists one such as `carry_lookahead`. `rsdb categories` shows the standard categories with their measures, designs, flags, and aliases, and `define-category`, `define-design`, `define-flag`, and `define-alias` add to them; see [glossary.md](glossary.md). A flag is a yes-or-no fact a category's builds record, such as an adder's carry in or a shift register being bidirectional; the details form shows the chosen category's as tick boxes, a build's page lists the ones it has, and search finds them, as in `bidirectional` or `cin`. `--design` sets the design and `--flag carry_in`, repeated, the flags; `add` also sets the carry flags the file's signs show. An adder's Carry in and Carry out are not typed but read from its file, as its width is: ticked for a magenta control line and a pink status line, which need no signs; see [conventions.md](conventions.md).
- Tags must exist before use; `define-tag` creates one. A tag is named in full words joined by underscores, and may also get a short token. Commands accept a tag by name or by token. A name with spaces needs quotes, as in `just rsdb tag 23a9 "carry lookahead"`.
- `--builder` records an in-game name of someone who built it, and repeats for a build with several builders, kept in the order given. Giving `--builder` to `set` replaces the stored builders. `--contributor` does the same for people who helped without building it, such as with the design.
- Width, latency, builders, and build date may be left unknown. The generated filename omits an unknown width.
- `--description` stores free text about the build, such as how to use it. The build's page shows it under the title, and search matches words in it.
- `--imported-by` records the in-game name of whoever imported the build. It is shown on the site.

## Website

The server is built from `template-site`: axum, maud, and sqlx over the same `redstone.db`. Pages are server-rendered HTML with forms. [fixi](https://github.com/bigskysoftware/fixi), vendored as `static/fixi.js`, sends a form or button that changes part of a page and swaps in the HTML fragment the server answers with; `static/app.js` is its one set of policies for every page: an error, an empty answer, or a page never replaces part of one, the page's one notice region says what went wrong or, from an `FX-Notice` header, what was done, a live panel (`fx-trigger="redraw"`) takes only an answer that is itself and is redrawn when an answer's `FX-Redraw` header names it, `fx-trigger="poll"` asks every few seconds, and focus stays where it was. Handlers tell fixi's requests by their `FX-Request` header, answering a fragment, and a plain form with a redirect. Fixi drives the build page's simulation while it runs, which redraws the failure banner and details once it is in; Send to Schemati; the details form's simulation result; the Schemati page's files; and the users page's rows. `static/form.js` adds the details form's category menu, pill fields, date boxes, and checks, and `static/sidebar.js` fits the category sidebar to the window.

```sh
cp .env.example .env
just serve
```

- `/?q=register+vertical+alpha+-torchless` narrows the list to builds matching every word. A word names a category, orientation, tag, width such as `8b` or `8 bits`, latency such as `3t` or `3 ticks`, builder, contributor, or importer, `stackable`, or `sync` or `unsync`, and the encoding is `encoding:bin` or `encoding:hex`; a plural finds its singular, as `adders` does. A word that names none of those matches part of a build's name, description, or credited names instead, so `owen` finds Owenage_'s builds. `-` or `not` before a word leaves those builds out, quotes or underscores keep a multi-word tag together, and a number before a unit, as in `3 ticks`, is one word. `rsdb search` takes the same words.
- `/` shows every schematic as a card with a thumbnail, its name, tag badges coloured by kind, and its latency, size, volume, and builders. `/?view=list` shows the same schematics as a table instead.
- A sidebar lists each category with how many builds match the search, such as Adders and Multipliers, under its section: Arithmetic, Logic, Gates, Conversion, Memory, Display, and Wiring, with every category off the list last, as Other. `rsdb define-category --section` puts a new category in one; `/?category=adder` shows only that category, and every category off the standard list is grouped under Other, `/?category=other`. Separate parameters narrow together, and commas within one mean any of them, as in `/?category=adder,subtractor`. `/?tag=alpha` shows builds with that tag; `tag` may repeat, each needing a match, so `/?tag=alpha&tag=torchless` is both and `/?tag=alpha,torchless` either. `/?sort=` takes fields separated by commas, each with `-` for descending: `added_at`, `volume`, `latency`, and `downloads`, as in `/?sort=-downloads,volume`. The default is newest first, ties fall back to it, and an unknown latency goes last either way. The page offers Newest, Volume (smallest first), Latency (fastest first), and Downloads (most first). The links keep the search, category, sort, and layout together. Tags link to their tag filter, builders and contributors to their player pages, and a build page's other details to a search for them; a search may name a person in a role, as in `builder:embizone`, `contributor:alex_you`, or `importer:lookaside`, and a build's category links to that category's list. Categories are listed alphabetically. A category such as Bussing lets each build give its own name, which the details form asks for and the build's title uses, as in 8-bit Bus Crossing. Each standard category stores its plural, such as `ALUs`; `rsdb define-category --plural` sets it, and otherwise it is the label with an `s`.
- An account's picture, on its profile, in the users list, and in the header, is its player's head when Mojang knows the player: `/heads/<uuid>` crops the face and hat from their skin into an 8×8 PNG, kept six hours in memory and a day in browsers, which pages scale up pixelated. Without one, the Discord avatar shows instead. Saving a Minecraft name on a profile asks Mojang for its spelling and UUID and refuses a name no player has; `rsdb respell` brings every stored name to its player's spelling.
- `/players/<name>` is a Minecraft player's page, whether or not they have signed up: their head, the builds crediting them as builder or contributor, the records they hold, and their account once an admin confirms the name as one's. Any name the site credits has one, and every credited name links to it; the address takes the spelling credited, so other capitals redirect there. Mojang is asked about each player at most every six hours.
- `/about/categories`, linked from About, explains how builds are sorted for the people using the site: categories as functions under their sections, listed from the database, designs, measures, the facts a build has, flags, tags, search, size per copy, and similar builds. Its text is in `src/web/pages/sorting.rs`; change it when the rules it describes change.
- `/leaderboards` ranks people: by builds credited to them as builder, by builds they added, an upload counting for its account under its confirmed Minecraft name and an import for its importer, and by records held. A record is first place, as fastest or smallest, on a board of at least two builds of one standard category, width or, for a serial category, throughput, logic, encoding, orientation, and design; a tie gives every holder one. The home page's Leaderboard tab leads here.
- `/leaderboards/<category>` ranks a standard category's builds against those they compete with: the same value of each of its measures, such as width, then stateless or stateful alike, the same encoding, orientation, and design, as in `/leaderboards/adder?width=8&orientation=vert&design=carry_cancel` or `/leaderboards/threshold?width=8&at_least=3`; a sequential multiplier never meets a combinational one. Each choice left out falls to the most common one, except that every design is ranked together unless one is chosen, as a category's designs all do its one job. It shows the fastest, the smallest, and the builds most compact at each latency, each smaller than every build at least as fast. A tie shares a place, and a build of unknown latency appears only by size. A category's list and its leaderboard link to each other as tabs.
- `/schematics/<id>/thumbnail.png` draws the build from the south-east and above, one flat colour per block. It is rendered from the stored file on request; cards link to it with the file's hash in the URL, so browsers cache it until the file changes.
- Builds of one category are compared for how alike they are, in `src/similarity.rs`: the share of their redstone components, each the same kind facing the same way, that line up once one is turned, mirrored, and shifted to fit the other best, so filler blocks and power are left out. Every pair of like components votes for the shift that lines them up, so the best shift is found rather than guessed. A build's page lists, under Similar builds, those of its category that are at least 90% alike, the most alike first: among the stored adders, copies and small fixes of one build score over 90%, while a builder's revisions of a design score 70% to 77% and different builds mostly under 60%, so they are not listed. Scores are kept in the `similarity` table, and a build whose file or category changed is compared again, in the background once the site starts or a build is published or edited, and after every `rsdb` command; comparing every build takes about five seconds. The upload preview warns, without holding up publishing, when a stored build of about its size is at least 90% alike, and offers a new version of it instead.
- `/schematics/<id>`, laid out in `src/web/pages/build.rs`, shows beside its title what the simulation found as a badge, passes, fails, simulating, or not simulated, whose popup on hover or focus gives the cases right or wrong, or the reason; a failing build's red tag, which leads it in listings, is left off its own page. Beside the 3D viewer come its key facts, large: its measures such as width and capacity, latency, blocks, with a stackable build's per-copy shape under its blocks per copy, size, and the release it works from, its hover naming the part that needs it, such as a target block; then its tags, its specs, including how it stacks, with what the simulation found about stacking in a popup on hover, and whether it is synced, and its credits, its build date and the file's dates written out, such as July 1, 2022, each builder, contributor, uploader, and importer a badge with their Minecraft head from `/players/<name>/head.png`, with the file's name, dates, downloads, and conventions folded under File. A blue check badge marks what the simulator checked, such as a category whose test passed, a width it confirmed, or a latency and synchronized it measured, and what was read from the file, such as a width, orientation, encoding, or adder's carry lines the file sets; a legend under the facts calls it auto-verified, its hover saying by the simulator or from the file, and what has no badge is as typed. A yes or no, such as synchronized, stateless, or a category's flags, shows as a small pill, green-tinted for yes and neutral for no, since a build without a trait is not wrong; a yes links to the builds that share it. In red and linking to the simulation, `fails simulation` marks the category of a failing build, and `not found by simulation` a register's typed stacking when its search found no step that works. Below, the simulation: for a failure, how many cases were wrong, with what was tried, which output bits were wrong, and the first wrong cases with the wrong digits marked; for a pass, its timing: any input that may change later than A, each output's first change, settling tick, and glitches, whether it is synced, with an example glitch, how soon most changes settle, and each bit's timing for an output that changes unevenly. Its inputs and outputs follow in the same column, above its description: two short lists read from the file, each unsigned line named for what its category's test takes it to be, by `simulate::name_lines`: an adder's or a carry out's lone magenta and pink lines its carry in and carry out, an incrementer's its increment and carry out, a decrementer's its decrement and borrow out, and a register's data buses data in and data out with each magenta line a write, on a button, or a read, on a lever, each entry with a swatch of its colour and its bits: a row of numbered lines such as a memory's `read 0` to `read 15` is one entry, `read 0–15`, saying when a number is signed twice, and an input gives the strength its signs ask for and whether it is inverted, as its levers are saved on. Any conventions the file breaks are listed below the simulation. A failing build's card or row in every listing leads its tags with a red `fails simulation` badge. The upload preview and the edit page show the same simulation section, run again by `static/form.js` whenever the category or width changes, first the cases and then, once they pass, the timing, so a mistake shows before publishing; a failure does not stop it. A timing no longer waited for, because the category or width changed again, stops.
- `/schematics/<id>/edit` is where a mod or admin, the build's uploader, or a confirmed builder of it edits its details and tags, laid out like the upload preview. The build's page links to it with an Edit button.
- A new version replaces a build's file to fix it, chosen on its edit page under Upload a new version, which `/schematics/<id>/versions/new` opens, by file, Schemati link, or file from one's own Schemati folder, as on the upload page. The edit page then shows the new file with the build's details, and saving publishes the version and any change to the details together, with an optional note on what it fixes. The new file must break no building convention the current version keeps, and keep at least 90% of its blocks, or change at most 10; within that, its inputs and outputs may move and its size may change. Blocks are compared without the power a resave changes, such as dust's strength, though a lever's position counts, at the shift of up to three blocks that lines them up best. Two different 8-bit carry-cancel adders share at most 14% of their blocks, so anything more is a build of its own. Publishing keeps the build's details, credits, tags, and downloads, counts as an edit, and simulates the new file. A build's page lists its versions, numbered from 1 with their dates, uploaders, and notes, once it has more than one, and each earlier one downloads from `/schematics/<id>/versions/<n>/download`. `rsdb new-version <id> <file> --note …` does the same from the command line, and `rsdb show` lists the versions.
- The upload preview, the edit page, and the edit page with a new version waiting share one layout: a Checks panel over the details form, beside the 3D viewer. Each has the same file chooser under the panel, as on the upload page: Choose a different file on the preview and with a version waiting, and Upload a new version on the edit page. Its fields belong to the details form, which is sent as multipart, so checking a file chosen there comes back with the details, tags, and note as typed; a file that cannot be read keeps the one shown, with why beside the chooser. The panel lists each check and how it stands: reading the file, the building conventions, a duplicate file, whether a new version is the same build, then the simulation and its timing, which `static/form.js` runs as the category and width are chosen, with a spinner while they do. Publish or Save waits for the simulation's result, though not its timing, and stays held, with the reason beside it, for a duplicate, a new version that is not the same build, or broken conventions until “follows its own layout” is ticked. Publishing or saving answers at once: the cases and timing run again in the background, one run of cases and one timing at a time, so cases never wait behind a timing; and the build's page shows a spinner while they do, its `static/simulation.js` asking `/schematics/<id>/simulation` every three seconds, 202 while they run, 200 with the result, 204 for a build with no test. Asking starts them again if nothing is running, as after a restart.
- The viewer is [schematic-renderer](https://github.com/Schem-at/schematic-renderer), loaded from jsDelivr together with its vanilla resource pack. The pack is about 7 MB and the browser caches it after the first view.
- `/schematics/<id>/download` returns the stored file under its generated filename. A build's page also shows when it was uploaded and, once a person has changed its details on the edit page or with `rsdb set`, when it was last edited. Each download is counted and shown on the build's page; the 3D viewer fetches the file with `?preview=yes`, which is not counted, and neither is a HEAD request. For a stackable build, a count per direction, such as `?west=7&north=3`, returns the copies joined, and `?markers=yes` adds a glass block off each corner for WorldEdit. The page's Download button opens a dialog with both choices.
- `/similar` finds the stored builds most like a file without uploading it: a file, a Schemati link, or, logged in, a file from one's own Schemati folder, read as it is, with no conventions checked and nothing kept. It lists the 20 builds of any category that share the most redstone with it, by `similarity::permille`, each with its thumbnail, facts, and share. Builds are compared from the most a build could share down, the smaller's components all lining up, so the comparing stops once no build left could make the list. Through fixi only the results change, and the search button says it is comparing while it runs.
- `/upload` lets anyone logged in upload a build, theirs or someone else's: choose a file, paste the link `//download <name>` gives on the Open Redstone Engineers server, which the site fetches from Schemati, or, with a Schemati session given on `/schemati`, pick a file from one's own Schemati folder, a file chosen or link pasted being taken first; optionally standardize it or keep where it pastes from, check the preview of what the site reads from it, fill in its details and tags, and publish. The category is typed, with the standard ones suggested in sidebar order and matched by name or label in any capitals; a name of one's own makes a category off the list. Uploads go live at once.
- `/schemati` opens the viewer's own Schemati folder, the one `//save` and `//load` use in game, once they paste the `sessionId` cookie Schemati's Discord login sets; the site checks it opens a folder before keeping it, until they disconnect or give another, and asks for a new one when Schemati forgets it. It lists the folder's files to download, publish through the upload preview, rename, or delete, and takes files to add, refusing any that is not a gzipped schematic, renamed to the letters, digits, underscores, and dots Schemati allows. A build's Download dialog has Send to Schemati for anyone logged in, which saves the file its choices make under its download name. Saving over a file of the same name replaces it and says so; renaming onto one is refused. Schemati has no API, so the folder is read from its listing page, and each change is the request its own page would make, judged by where Schemati redirects next.
- The details form's Stacking section marks a build stackable: each row is a direction (west, up, north, or west and up), the blocks from one copy to the next, and optionally the most copies. A second row is for a build that also stacks another way. The first row starts from the build's size the way its bits run, and saving stacks two copies each way, each pasted over the one before as `//rstack` does, and refuses a step whose copies collide, a solid input or output block on a different solid block.
- Builders, contributors, and tags are typed as pills: pick a suggestion, or type a new name and press Enter, and × removes one. A builder or contributor must be a Minecraft player Mojang knows, and is stored as they spell it; a name no player has is refused, unless Mojang cannot be reached, when names are kept as typed. Only an admin may name a new tag, which is of the `other` kind; anyone else picks from the tags there are, and the server refuses a new one from them. The build date is a box each for year, month, and day, always in that order; typing moves from one to the next without dashes, a whole date pasted into any of them fills all three, and leaving them with a part missing, a day the calendar lacks, or a day still to come says so beneath them and keeps the form from being sent. It has a "Don't know" box. Synchronized is a toggle, on for a new upload; for a stored build where it is unknown, the toggle shows a dash and saving leaves it unknown until it is clicked. Without scripting, the boxes take one value each and the server checks everything again.

### Accounts

People log in with Discord; an account is made at their first login. Each account has a role:

- **user** uploads builds. Anyone logged in can give their Minecraft name on their profile, at `/users/<username>`; the profile then lists the builds credited to it as builder, then as contributor, above the builds the account uploaded. One name belongs to one account, whatever its case. A user may edit the builds they uploaded, and, once an admin confirms their Minecraft name, the builds crediting it as builder: their details and tags, and new versions.
- **mod** also edits any build's details and tags.
- **admin** also deletes builds, from the Delete button on a build's page, and sets roles, at `/users`.

Discord login needs `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`, and `DISCORD_REDIRECT_URI` in `.env`; see `.env.example`. The redirect must also be listed on the app's OAuth2 page in the Discord Developer Portal. Without them the site still runs, with login turned off.

The first admin is made from the command line, after they have logged in once:

```sh
just rsdb users
just rsdb role <discord username> admin
```

- Styles are Tailwind. `styles/app.css` is the source, and `just css` builds `static/app.css`, which is committed so the server and the Nix build need no Tailwind. `just serve` rebuilds it first, and `just check` fails when it is stale.

After changing a query, run `just prepare` to refresh the offline query metadata in `.sqlx/`.
